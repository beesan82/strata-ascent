> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 歩行敵・固定砲台が見えている範囲・近傍でいきなり現れたり消えたりする症状を、選定の窓依存(窓端で切れたランの開始位置・長さ、密度の代表の入れ替わり)と選定外実体の即時破棄という真因に対して直す。

**Architecture:** 敵選定(`chooseSpawns` / `chooseTurretSpawns`)に渡す床ランを `src/world/infra.ts` の `canonicalRun` で正規化する。2.17 の飛行敵の保持(`retainFlyers` / `newFlyerSpawns`)を、種別を問わない純粋関数 `retainHeld` / `newHeldSpawns`(実体からスポーンアンカーを引く関数を受け取る)へ一般化し、飛行敵はその薄い包みにする。歩行敵・砲台は実体にスポーンアンカーを持たせ、`retainEnemies` / `newWalkerSpawns` / `newTurretSpawns` で同じ規則を当てる。選定関数そのもの(出現率・密度・保護点・広間の規則)は変えない。

**Tech Stack:** Vite + TypeScript、Vitest。コメントは日本語。

**Spec:** `docs/superpowers/specs/2026-11-11-enemy-stability-design.md`

## Review Focus

3. **密度が倍にならない**: 保持した個体の隣に別の代表が湧かない。保持と新規出現を繰り返しても密度上限と砲台・歩行敵の近接除外が破られない(Task 2)。

## 実装時の裁定

1. **正規化は一度だけ求めて敵とインフラで共用する。** `refreshInfra` が建設者・端末のために求めていた `canonicalRun` の結果を `refreshEnemies` へ移し、引数で渡すようにした。`canonicalRun` は冪等ではない(延長が上限 64 に達したランを再び渡すとさらに延ばす)ので、二重適用を避ける意味もある。走査コストは従来と同じ(正規化の回数は増えていない)。
2. **補給キャッシュ・武器庫・トラムは正規化前のランのまま。** 設計の範囲は敵選定だけで、キャッシュ・武器庫は `holdSpot` の粘着で対処済み。正規化するとキャッシュ・武器庫の ID と位置が変わり、開封記録(`claimedSupplyCaches` / `claimedArmories`)の既存の ID と食い違うため触らない。
3. **正規化で延びたランの出現位置は窓の外になり得る。** ラン内オフセットは正規化後の長さで決まるので、出現位置が窓(±40)の外、最大で窓端から 64 タイル先になることがある。窓の外は画面の外なので「見えている所で湧く」症状は増えない。選定に入っている間は距離によらず保持する(保持半径の判定より選定が先)。
4. **歩行敵の保持の距離はスポーンアンカーで測る(個体の現在位置ではない)。** 飛行敵と同じ。歩行敵は歩いてアンカーから離れるが、捨てる・残すはアンカーとプレイヤーの距離で決まる。アンカーは実体の要素に `anchor` として持たせた(`Walker` のクラスには触らない)。
5. **新規出現の抑止に砲台・歩行敵の近接除外(3)を両向きに当てた。** 従来は「歩行敵の選定が砲台を退ける」片向きの規則(`chooseTurretSpawns` の occupied)だった。保持を入れると、(a) 選定外で保持している歩行敵の隣に新しい砲台が湧く、(b) 保持している砲台の隣に新しい歩行敵が湧く、の 2 つが起きうる。(a) は `newTurretSpawns` で場の歩行敵全員のアンカーを見て止め、(b) は保持している砲台を退けると保持が破れるので `newWalkerSpawns` で歩行敵側を止める。数値(チェビシェフ 3)は既存のまま。選定関数に渡す occupied は今回の歩行敵の選定だけにして、選定そのものは窓だけで決まる純粋関数のまま保った。
6. **砲台の地区ゲート。** ゲートが閉じた地区へ入った瞬間に全消去していた分岐を、選定を空にした保持規則に置き換えた(飛行敵と同じ。ゲートは新規出現だけを止める)。
7. **保護点。** 休憩点の保護範囲はプレイヤーの移動で入れ替わる。選定時は保護外だった個体が新しい保護範囲に入っても、保持を優先して残す(設計どおり、保護点は新規出現だけを止める)。
8. **保持の一般化の形。** `retainHeld` / `newHeldSpawns` はアンカーを引く関数(`anchorOf`)を受け取る。飛行敵の実体(`{ spawnId, flyer }`)の形とテストを変えずに同じ関数へ寄せるため。`FLYER_HOLD_RADIUS` は `ENEMY_HOLD_RADIUS`(64)の別名として残した。
9. **テストは新しいファイルに分けた。** `spawn.test.ts` は選定の規則、`flyerHold.test.ts` は飛行敵の保持なので、歩行敵・砲台の正規化と保持は `enemyHold.test.ts` に置いた。実地形(seed 20260711)での再現は地形生成に依存して壊れやすいので、窓端で切れるランを人工的に作った地形で固定した。

## 保留

1. **`canonicalRun` の延長上限(64)。** 窓の外へ 64 タイルを超えて続くランは、延長が上限で止まるため左端・長さがなお窓の位置に依存する。そうしたランから決まるスポーンは ID と位置が揺れうる(保持半径内なら保持で見た目は止まる)。上限は建設者と共用の値なので今回は変えない。
2. **窓の中で 5 タイル未満に切れたランは候補に入らない。** `findFloorRuns` は正規化の前に最小長(5)で切るので、窓端に 1〜4 タイルだけ掛かったランは候補にならず、窓がさらに進むと現れる。現れたときの ID と位置は正規化で一定なので症状には効かないが、選定の候補集合はなお窓に依存する。
3. **密度の代表の入れ替わり(選定の貪欲さ)そのもの。** 正規化で各候補の ID・位置は窓に依らなくなったが、列挙順の貪欲な密度判定は窓に入っている候補の集合に依存するので、代表はなお入れ替わる。今回は保持で見た目を止めた。セル単位の argmin などで選定を窓非依存にする案は、出現の分布と密度が変わるため範囲外(2.17 の保留 2 と同じ)。
4. **保持中の個体数。** 保持半径 64 の内側に窓の外になったアンカーの個体が残るため、同時に生きている歩行敵・砲台が従来より増えることがある(密度上限は守る)。性能・難度に効くほどかは実機で見て判断する。
5. **保持個体を撃破した後の繰り上がり。** 保持個体を倒すと、その個体が締め出していた近くの選定が次の走査で湧くことがある。2.17 の裁定 4 と同じ性質で、撃破記録の規則は変えていない。
6. **既存の撃破記録との互換。** 窓端で切れたランから決まっていた歩行敵・砲台の ID(`w:<窓端>,<行>` など)は、正規化で本来の左端の ID に変わる。2.17 以前の撃破記録(`defeatedEnemies`。保存される場合はセーブも)にある窓端由来の ID は一致しなくなり、その個体は再び出うる。窓端由来の ID はもともと窓の位置で変わる不安定な ID だったので移行はしない。保存の有無と影響は未確認。
7. **実機での最終確認。** 設計書の実証(seed 20260711、(196,120) から横へ歩くと `w:216,136` が dx=60 で現れ dx=64 で消える)が解消したかは、親側の実機またはスクリプトで確かめる。
