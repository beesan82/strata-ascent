# 2.17 前半「飛行ドローンの粘着保持」 実装計画

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 飛行ドローンがチカチカして瞬間移動を繰り返す症状を、出現選定の窓依存という真因に対して直す。生存中の飛行敵は、スポーンアンカーがプレイヤーから保持半径(チェビシェフ距離 64 タイル)以内なら、選定から外れても捨てない。

**Architecture:** 保持の判定を `src/world/spawn.ts` の純粋関数 `retainFlyers` に切り出し、保持した個体と重なる新規出現の抑止を `newFlyerSpawns` に切り出す。`main.ts` の `refreshEnemies` はこの 2 つを呼ぶだけにする。選定(`findAirPockets` / `chooseFlyerSpawns`)そのものは変えない。

**Tech Stack:** Vite + TypeScript、Vitest。コメントは日本語。

**Spec:** `docs/superpowers/specs/2026-11-11-flyer-stickiness-design.md`

## Global Constraints

- 出現率・密度(32×16)・行動(巡回/追尾/諦め)の数値は一切変えない。
- 歩行敵・固定砲台は対象外(保留に記録する)。
- 撃破済みの扱いは現行どおり(`defeatedEnemies` で再出現しない。死体は撃破処理で即除去)。死亡・復活時に実体を全て捨てる処理も現行どおり。
- 描画には触らない。性能への影響は既存配列のフィルタだけ。
- 完了条件: `npm test`、`npx tsc --noEmit`、`npm run build` が通る。

## Review Focus

1. **窓をずらしても保持半径内の個体が消えない**: 開けた空間(全面空気)で窓を 1 タイルずつずらす走査を繰り返し、前回の個体のうち保持半径内のものが同じ実体のまま残ることをテストで固定する(Task 1)。
2. **密度が倍にならない**: 保持した個体の隣に、窓のずれで選ばれた別の代表が湧くと、個体数が増えるうえ「少しずれた位置に別の個体が出る」症状が残る。保持個体の 32×16 の内側の選定は新規に湧かせない(Task 1 の `newFlyerSpawns`)。
3. **地区ゲートの境界**: 倍率 0 の地区へ入った瞬間に全消去していた分岐を、保持規則に置き換える(Task 2)。

## 実装時の裁定

1. **保持の距離はアンカーで測る(個体の現在位置ではない)。** 設計どおり。追尾中の個体はアンカーから離れてプレイヤーに付いてくるが、捨てる・残すはアンカーとプレイヤーの距離で決まる。保持半径 64 は走査窓(±40 × ±24)より広いので、窓から外れたアンカーもしばらく残り、遠ざかってから捨てられる(64 タイル先は通常の画面の外になる想定。眺望ズームでの見え方は未確認)。
2. **今回の選定に入っている個体は距離によらず残す。** 選定のアンカーは窓の中にしか無いので実際には常に半径内だが、判定の順序を「選定に入っている、または半径内」として明示した。
3. **新規出現の密度抑止(`newFlyerSpawns`)を足した。** 設計書は保持だけを規定しているが、保持だけでは「窓のずれで選ばれた別の代表」が保持個体の隣(32×16 の内側)に湧き、密度が倍になったうえ「少しずれた位置に別の個体が出る」症状が残る。保持個体のアンカーから 32×16 の内側にある選定は湧かせないことにした。密度の数値は変えず、既存の密度規則を保持個体にも当てるだけ。選定どうしは `chooseFlyerSpawns` が密度を満たしているので、選定に入っている保持個体が他の選定を締め出すことはない。これにより「場の個体どうしは常に密度上限を満たす」が不変条件になる(Task 1 のテストで固定)。
4. **保持個体を撃破した後の繰り上がり。** 保持個体を倒すと、その個体が締め出していた近くの選定が次の走査(最大 30 フレーム後)で湧くことがある。これは窓が動いたときに従来から起きていた置換と同じ性質で、撃破記録(選定後の減算)の規則は変えていない。
5. **保護点の変化。** 保護点のうち休憩点は「最寄りの休憩点」なので、プレイヤーの移動で入れ替わる。選定時は保護外だった個体が、新しい休憩点の保護範囲に入っても保持を優先して残す(地区ゲートと同じく、保護点は新規出現だけを止める扱い)。
6. **死亡・復活では従来どおり全て捨てる。** 復活点へ瞬間移動するので、保持の対象外。
7. **テストは新しいファイルに分けた。** `spawn.test.ts` は選定の規則のテストなので、`refreshEnemies` の手順を再現する保持のテストは `flyerHold.test.ts` に置いた。

## 保留

1. **歩行敵・固定砲台の窓依存の可能性。** 両者は床ラン(`findFloorRuns`)からの選定で、ランは最大ラン(行ごとに左から連続を取る)なので飛行敵のポケットほど窓依存は強くない。ただし窓の左右端で切れたランは `x`(= ID)と `len`(= ラン内オフセット)が窓の位置で変わり、`chooseSpawns` / `chooseTurretSpawns` の ID と位置が揺れる。さらに選定は列挙順の貪欲な密度判定なので、端のランの出入りで密度チェーンが変わり、窓の中央付近の個体まで入れ替わる余地がある。建設者・端末は `canonicalRun` で端のランを揃えて対処済みなので、同じ手当て(`canonicalRun` の適用)か、飛行敵と同じ保持規則の適用が候補。症状の報告と実証(窓をずらして ID 集合を比べるテスト)を先に取ってから判断する。
2. **飛行敵の選定そのものの窓非依存化。** 今回は保持で症状を止めたが、選定(列挙順の貪欲)は窓依存のまま。ポケットをグリッドに量子化する、またはセル単位の argmin で代表を決めると窓に依存しない選定になるが、出現の分布と密度が変わるため今回の範囲(数値を変えない)の外。
3. **保持中の個体数の上限。** 保持半径 64 の内側に、窓の外になったアンカーの個体が残るため、窓の中だけで数えた従来より同時に生きている個体が増えることがある(密度上限は守る)。性能・難度に効くほどかは実機で見て判断する。
