# 設計書: タッチ操作の全面改修(ツインスティック回帰 + 視線=照準/カメラ先行の統合)

状態: ユーザー承認済み(2026-11-04)。第1弾の実機評価(2026-11-04)を受けた改修。
置き換え対象: 2026-11-03-touch-redesign-design(モード分離 + 直接ポインティング)のうち
移動・パルス・眺望の部分。重粒子砲の扱いは本書でも維持する(§3)。

## 1. 根本原因(コード裏取り)

「視線が変えられない」は感覚ではなく、現行実装の構造そのもの:

- **パルスの照準が移動入力に従属している。** `pulseAimDir(input.state, facing)`
  (entities/pulse.ts)は移動キーから 8 方向を作るだけなので、「止まって上を狙う」
  「左を向きながら右上に撃つ」が原理的にできない。上を狙うには ↑ を押すしかなく、
  それは梯子入力でもある。照準の独立した入力チャンネルが存在しない。
- **眺望がタッチでは実質死んでいる。** 手動眺望(view.ts)は Shift + 接地 + 静止で
  aimX/aimY 方向へパンするが、タッチでは aim が「タッチ照準点(砲ドラッグ中のみ)」
  か「向きの水平」のどちらかしか入らない(main.ts の aim 合成)。つまり 望 を長押し
  しても正面水平にしかパンできず、見たい方向を選べない。
- **カメラに先読みがない。** Camera.follow はプレイヤー中心(+眺望オフセット)だけを
  追い、照準方向への寄りがゼロ。狙っている先が見えない。
- 移動ボタン方式の認知負荷(ボタンを目で探して押し分ける)は touch-redesign 設計書
  自身が旧方式の失敗要因として記録済みで、現行方式でも解消していない。

## 2. なぜスティックが捨てられたか、なぜ今度は成立するか

過去の経緯(docs/superpowers/specs/2026-11-03-virtual-stick-design、
aim-stick-design、touch-redesign-design):

- 浮動スティック(移動のみ、PR #15)はユーザー要望で入れたが照準が未解決だった。
- ツインスティック化(PR #16)が見送られ #17 のモード分離になった理由は 3 点:
  1. 重粒子砲の「倒す=狙い+溜め、離す=発射」を 1 本の指に結合すると、狙いを
     やめる動作が誤射になる。掘削は地形に恒久反映され誤射コストが高い。
  2. 当時は敵なし・時間圧なしで、ツインスティックの 3 点同時操作に見合う
     場面がなかった。
  3. 浮動原点 + 最大 42px ストロークでは角度分解能が足りず、指と土台円が
     狙う地形を隠す。

今回の前提変化: パルス(掘れない・撃ちっぱなし無料・離せば止まるだけ)が第1弾で
入り、歩行敵がいて、第2弾の飛行敵には自由照準が必須になった。理由 1 は
「スティックに載せるのはパルスだけにし、重粒子砲は従来の専用経路に残す」で回避
する(§3)。理由 2 は敵の存在で解消。理由 3 は固定寸法の拡大とカメラ先行(§4)で
手当てする。

## 3. 新操作系の全体像

| 入力 | 操作 |
|---|---|
| 左仮想スティック | 画面左 45% の任意の点に触れると浮動で出現(土台 112px、ノブ 52px、最大ストローク 56px)。倒し量をデジタル変換して移動キー相当(←→↑↓)として Input に流す |
| 右仮想スティック | 画面右 45% の任意の点に浮動で出現(同寸法)。方向 = パルスの照準(アナログ)、倒し量が発射閾値を超えたら連射 |
| 跳 | 右下の固定ボタン(84px)のみ残す。スティック出現ゾーンからボタンの領域は除外(ボタン優先) |
| 重粒子砲 | 従来どおり専用ボタン(76px): 押下で溜め → 指ドラッグで照準点を指す → 離して発射、中心 38px 圏内に戻して離すとキャンセル(cannonPhase / Graviton.cancelCharge は無変更)。溜め中は左スティック入力を無効化する(現行の「止まって狙う」モード分離を維持) |
| 眺望 | 望 ボタン(48px、右上)は残すが意味を変える: 押している間、右スティックの方向へ手動眺望パンする(§4)。従来の「正面水平にしか行けない」問題を解消 |

- スティックは各 1 本の指(pointerId)だけを受け付け、ボタンとは独立に多点同時
  操作できる(移動 + 照準 + 跳 の 3 点同時は第2弾の飛行敵戦で必要になるため許容
  する。根拠は §2 の前提変化)。
- アナログ量は移動速度に反映しない(最高速 6 タイル/秒は不変)。スティックは
  あくまで方向キーのオン/オフへの変換 + 照準ベクトルとして使う。
- 梯子: 左スティックの縦倒しを ↑↓ 入力に変換する。縦の閾値は横より高くし
  (歩行中の誤った梯子入力を減らす、旧 stickKeys と同じ思想)、梯子近接時のみ
  登攀が起きるのは Player 側の既存仕様どおり。梯子ボタンの表示切替
  (setTouchLadderVisible)は廃止する。

## 4. 「視線」の仕様(照準とカメラ先行の統合)

視線 = 「右スティックが指す方向」と定義し、照準・向き・カメラを一つの
ベクトルで駆動する。

- **照準ベクトル(アナログ自由方向)**: 右スティックの単位ベクトルをそのまま
  パルスの発射方向にする。8 方向固定はタッチでは廃止(PC のキーボードは従来
  どおり pulseAimDir の 8 方向、§5)。弾の物理(掃引衝突・射程 14・速度 30)は
  任意方向を既に扱える。敵 HP 3 / 威力 1 は変更しない。アナログ化で歩行敵は
  若干当てやすくなるが、第2弾の飛行敵はアナログ前提の設計になるため許容する。
- **発射と照準の分離**: デッドゾーン(ストローク比 0.25)を超えたら照準として
  有効、発射閾値(0.55)を超えたら連射開始。その間は「狙っているが撃っていない」
  状態があり、照準コーン(既存のライトコーン = renderer.aimAngle 経路)と
  カメラ先行だけが動く。
- **照準の保持**: スティックを離しても最後の照準方向を保持する(次に倒すまで
  その方向を向き、パルスのフォールバック方向になる)。移動だけでは照準を
  リセットしない。「向きの水平」への自動復帰はしない — これが現行の
  「勝手に正面に戻る」違和感の元だったため。プレイヤーの facing は、右
  スティック有効中はその x 成分に追従する。
- **カメラ先行(ルックアヘッド)**: カメラ目標 = プレイヤー中心 + 照準方向 ×
  先行量。先行量は照準のみで 2.5 タイル、発射中・砲の溜め中は 5 タイルまで
  伸ばす(純粋関数で算出し Camera.follow の目標に加算)。指している先が画面に
  入るので、指の下に目標が隠れる問題(§2 理由 3)も緩和される。先行は
  view.ts の眺望オフセットとは別レイヤで加算し、眺望の状態遷移には触らない。
- **眺望(手動パン)**: 望 を押している間は viewState の manual 入力に右
  スティックの正規化ベクトルを渡す(aimX/aimY)。接地・静止の条件と移動キーで
  即解除の仕様は view.ts のまま。最大 40 タイルパン + ズームアウトは現行どおり。

## 5. PC(キーボード/マウス)との対応

- PC の入力経路には一切触らない。マウス照準(砲・コーン)、KeyJ/マウス左の
  パルス、pulseAimDir の 8 方向、Shift 眺望、すべて現行どおり。
- main の照準合成は優先順位を明示する: マウス(実座標) > 砲のタッチ照準点 >
  右スティック照準 > 保持中の照準 > 向きの水平。タッチ系の新しい入口は
  Input に追加するだけで、PC の分岐条件(mouseSeen 等)は変えない。
- スティック等の DOM は従来どおり `pointer: coarse` の端末でのみ構築する。
  PC 開始地点のスクリーンショット差分 0 を維持する。

## 6. 実装タスク分割(テスト先行)

入力まわりは純粋関数に切り出し、DOM は実挙動で確認する(AGENTS.md の方針)。

1. **純粋関数の切り出しと Input の照準チャンネル追加**
   - `stickVector(dx, dy, radius)`: デッドゾーン・正規化・ストローク比。
   - `stickKeys(vec)`: 横 0.35 / 縦 0.5 の閾値で {left,right,up,down} 化。
   - `pulseTrigger(mag)`: 照準有効(>0.25)と発射(>0.55)の判定。
   - `aimKeeper(prev, stickVecOrNull)`: 照準保持の状態遷移(純粋な reducer)。
   - `lookahead(aim, firing)`: 先行量(タイル)の算出と上限クランプ。
   - Input に `touchAimX/Y/Active`(単位ベクトル)と保持照準の入口を追加。
   - 検証: 上記すべて Vitest で固定(閾値境界・斜め・保持と非リセット)。
     `npm test` / `tsc` / `build`。
2. **左スティック DOM(移動ボタン群の置き換え)**
   - touch.ts に浮動スティックの汎用部品を作り、左ゾーンに設置。←→↑↓
     ボタンと ladder-on 表示連動を撤去し、stickKeys 経由で touchDown/touchUp
     に流す。溜め中の左入力無効化は現行のフラグ経路を流用。
   - 検証: Playwright タッチエミュレーションでドラッグ → プレイヤーが歩く/
     梯子を登る、離すと止まる。スクリーンショットで土台・ノブ表示を確認。
3. **右スティック DOM とパルスのアナログ照準**
   - 右ゾーンに設置。「射」ボタンを撤去。main のパルス照準合成を
     「右スティック有効ならそのベクトル、なければ従来 pulseAimDir」に切替。
     発射は pulseTrigger と Input.pulseHeld の OR に載せる。facing の追従。
   - 検証: Vitest(Input の合成・発射 OR)+ エミュレーションで 2 本指同時
     (左で移動、右上へ照準)で斜め上に連射され弾数が減ること、スティックを
     緩めると照準だけ残り発射が止まること。
4. **カメラ先行と眺望の配線**
   - main: Camera.follow の目標に lookahead を加算。砲ドラッグ中はタッチ
     照準点方向にも先行。viewState の manual 入力にスティックベクトルを
     合成(望 押下中)。望 の Shift 経由は維持しつつ aim の供給源を差し替え。
   - 検証: view.test.ts の既存ケース無変更で通過 + エミュレーションで右に
     照準すると画面が右へ寄る、望 + 右倒しでそちらへパンする。描画変更に
     あたるため前後スクリーンショットと frametime(render / stage の p50、
     前後 2 回)を取る。DOM オーバーレイ追加のみでキャンバス描画パスは
     増やさないことを確認。
5. **仕上げと実機確認ポイントの提示**
   - 旧ボタンの CSS(#touch 配下)を整理。touch.test.ts の cannonPhase は維持。
   - 実機確認ポイント: ①歩きながら斜め上に撃てる ②止まって真上を狙える
     ③狙った先が画面に入る(先行の効き) ④砲の誤射が増えていない
     ⑤梯子の誤登りが増えていない。これらを TestFlight ビルドで判定する。

## 7. リスクと切り分け

- **#17 で得たものの喪失**: 砲の誤射防止(モード分離とキャンセル)は本書でも
  砲をスティックに載せないことで保持。移動の確実性(ボタンの明示性)は失うが、
  それが今回の不満の本体であり、ユーザーの明示希望として受け入れる。
- **3 点同時操作の負荷**: 第1弾当時は不要だったが、飛行敵を撃ちながら逃げる
  第2弾では必須になる。跳 をスティックのフリック等に兼用させる案は、梯子・
  照準との競合が多いため採らない(ボタン 1 個は残す)。
- **浮動原点の暴走**: 出現ゾーンを左右 45% に限定し、右スティックの原点が
  跳・砲ボタンに重ならないようボタン側を優先(pointer capture はボタンが先)。
- **梯子の誤入力**: 縦閾値を高くする + 登攀自体は梯子近接でのみ起きる既存
  仕様で二重に防ぐ。実機で増えたら閾値だけを調整する(数値は定数に集約)。
- **決定論・描画制約**: 入力はリアルタイム系でワールド生成に触れない。
  スティック表示は DOM オーバーレイで、キャンバスの描画パス・焼き込みには
  相乗りしない。純粋関数は Vitest で固定し、Math.random は使わない。
