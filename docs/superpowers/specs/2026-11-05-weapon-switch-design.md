# 設計書: 武器切り替え式 — パルスと重粒子砲を右スティックに統合する

状態: ユーザー承認済み（2026-11-05、段階 1 から実装）。ユーザーの要望「パルスと重粒子砲を切り替え式にしてほしい」（2026-11-05）を受けた改修。ツインスティック操作（設計書 `2026-11-04-twin-stick-controls-design.md`、PR #31）の上に載る。

## 0. 前提の変更と、変えないもの

現行の設計方針は「重粒子砲は主武装の連射ローテーションに混ぜない。誤射すると地形に恒久被害が出るため、発射までの経路を意図的に重くしてある」であり、砲だけが専用ボタン経路（押下→溜め開始、ドラッグ→照準点、離して発射、中心に戻して離す→キャンセル）を持っていた。

ユーザーの明示の意思により、この分離方針は**変更する**。パルスと重粒子砲は「現在の武器」を切り替えて使う 2 つの武器になる。ただし砲の性質（地形への恒久被害、弾数 3・回復 6 秒/発という希少性）は変わらない。本設計は、切り替え式という枠の中で、誤射防止の重みを「経路の分離」から「モードの明示と発射操作の差別化」へ移し替える。

変えないもの（数値はすべて現行コードの実値）:

- パルスの仕様: 連射 6 発/秒（`PULSE_INTERVAL = 1/6`)、地形は掘れない。
- 重粒子砲の仕様: `CHARGE_TIME = 0.6` 秒、`MAX_CHARGES = 3`、`RECHARGE_TIME = 6` 秒、`BORE_LENGTH = 300`、`BORE_RADIUS = 3`。発射は「溜め完了後に離した瞬間」（`Graviton.update` の現行意味論）。
- スティックの基礎定数: `STICK_DEADZONE = 0.25`、`STICK_FIRE_THRESHOLD = 0.55`、`STICK_RADIUS = 56px`、土台 112px、ノブ 52px。
- 照準保持（`aimKeeper`）とカメラ先行（照準のみ 2.5 タイル / 拡張時 5 タイル）の枠組み。
- 描画の制約: 新しい描画パスを作らない。32 色量子化・決定論に触れない（本設計は入力系のみの変更で、ワールド生成には一切関与しない）。

## 1. 切り替えの操作文法（タッチ）

### 1.1 切替ボタン: 位置と形

- 現行の「砲」ボタン（76px 円、右クラスタの 1 段目、跳ボタンの左）を、**切替ボタンに置き換える**。位置・サイズ・右クラスタ内の並びは変えない（既存の指の記憶を壊さない。`index.html` の `.sz-cannon` 相当の枠を流用し、クラス名は `.sz-weapon` に改める）。
- ラベルは「切り替えた先」ではなく「**現在の武器**」を表示する（モード明示の主担い手。理由は §2)。パルス時 = 「パルス」(`76px` 円に収めるため font-size は 22px → 16px)、砲時 = 「砲」（HUD が正式名称「重粒子砲」を担う。ボタンは短縮表示と役割分担する）。
- 切り替えはボタンの**押下エッジでのみ**起きる（`Input.touchDown` のエッジ仕様と一致。長押し・連打では連続切り替えしない)。
- 指の動き: 右スティックは浮動式で、右親指がスティックを操作している間は同じ親指でボタンを押せない。つまり切り替えは「スティックを離した状態でのタップ」が自然な前提になる。この同時押しの物理的不可能性は、それ自体が安全策として働く（照準・発射の最中にモードが変わらない)。

### 1.2 右スティックの二つの顔

右スティックは現在の武器によって意味が変わる。照準（方向の決め方）は両武器で完全に共通で、変わるのは「発射の意味論」だけに絞る。

| | パルスモード（現行どおり） | 砲モード（新設） |
|---|---|---|
| 倒す（mag > 0.25） | 照準が有効になる | 照準が有効になり、**溜めが始まる** |
| 深く倒す（mag > 0.55） | 連射する（`pulseTrigger`) | （意味なし。溜めは深さでなく時間で進む） |
| 離す | 連射が止まる。照準は保持される | **発射**（条件は §1.3)。照準は保持される |
| 中心へ戻して離す | 何も起きない | **キャンセル**（§1.3) |

砲モードの文法は、現行の砲ボタンドラッグの素直な写像である:

- 「ボタンを押す」→「スティックを倒す」（溜め開始）
- 「ドラッグで狙う」→「スティックの方向で狙う」（アナログ照準、そのまま）
- 「離して発射」→「離して発射」（不変。発射は常に解放という能動操作が引き金）
- 「中心に戻して離すとキャンセル」→「デッドゾーン圏内へ戻して離すとキャンセル」（§1.3 のヒステリシスで判定）

パルスとの決定的な差は、**砲は倒しただけでは絶対に撃てない**ことにある。パルスの誤射は「倒しすぎ」だが、砲の発射には「0.6 秒以上倒し続ける」＋「離す」という 2 つの能動操作がそろって初めて成立する。これが切り替え式における砲の「重さ」の置き場所である。

### 1.3 砲スティックの位相（溜め・照準・キャンセル）

現行 `cannonPhase`（砲ボタンのドラッグ位相。`AIM_START_DIST = 24px` で aiming へ、`CANCEL_DIST = 38px` 圏内へ戻ると cancel、という非対称ヒステリシス）のスティック版を、ストローク比の位相関数として新設する。

- 定数: `CANNON_AIM_RATIO = STICK_DEADZONE`（= 0.25。溜め開始・照準有効の閾値。`stickVector` が 0.25 以下をゼロとして返すため、文法は自動的にパルス側と揃う）、`CANNON_CANCEL_RATIO = 0.45`（キャンセル圏。開始閾値より広いヒステリシス)。
- 位相は `'idle' | 'charging' | 'cancel-armed'`:
  - idle → mag > 0.25 で charging（溜め開始。同時に `Graviton` 側の held が立つ）。
  - charging 中に mag <= 0.45 へ戻したら cancel-armed（「中心へ戻した」状態。現行の cancel 予告色と対応）。
  - cancel-armed から mag > 0.45 へ再び出たら charging に戻る（現行 `cannonPhase` が cancel → aiming に戻れるのと同型）。
- **発射の成立条件**（スティックを離した瞬間に判定）: 「離す直前の位相が charging」かつ「`chargeRatio >= 1`（0.6 秒の溜め完了）」。これは現行 `Graviton.update` の意味論（held を離したとき、溜め完了していれば発射、不足なら不発）そのものであり、位相が cancel-armed なら現行の `requestFireCancel()` 経由で `cancelCharge()` してから離す（解放より先に溜めを破棄する現行の順序を踏襲）。溜め不足で離した場合は位相に関わらず不発（現行どおり。ペナルティなし、弾は減らない）。
- 現行砲ボタンとの数値の対応と差異（正直に明記する）: 現行の開始距離 24px はボタン中心からの絶対距離で、スティック比に換算すると 24/56 ≒ 0.43。スティック版の開始 0.25（= 14px 相当）は現行より早い。キャンセル圏は現行 38px（ボタン半径いっぱい）に対し、スティック版 0.45 × 56 ≒ 25px と狭くなる（= キャンセルしにくくなる)。この 2 つの差は次の 2 点で相殺できると判断する: (a) 発射には溜め開始の早さに関わらず `CHARGE_TIME = 0.6` 秒の熟慮時間が常に入る。(b) キャンセルは「中心へ戻して離す」以外に、溜め不足のまま離す（不発で終わる）でも実質的に果たせる。スティック版でキャンセルが要るのは「溜めが完了してしまったが撃ちたくない」ときだけで、その場合は 0.45 圏内へ戻す操作が残る。段階 1 のエミュレーション検証で、この 25px 圏への戻し操作が無理なく行えるかを確認項目に入れる（§6)。

### 1.4 発射方向の決まり方

発射方向は現行どおり `renderer.aimAngle`（ライトコーンと同一の角度）を `fire()` が読む。タッチ時の照準合成は、現行の「マウス > 砲のタッチ照準点（`touchPoint`) > 右スティック照準 > 保持照準 > 向きの水平」から、砲専用だった `touchPoint` の座に右スティック照準が入る形になる（スティック版では `touchPoint` を使わない)。

- 発射は「スティックを離した瞬間」の update で `Graviton.update` が `fire()` を呼ぶ。この時点で `touchAimActive` は落ちているが、`heldAim` は保持されたままなので照準合成は保持照準へ落ち、方向は維持される。`aimAngle` 自体が 1 フレーム遅延を許容する既存設計（renderer のコメントに明記）であり、離す直前フレームのコーン方向 = 狙った方向が使われる。現行の砲ボタン経路（離した瞬間に `touchUp('KeyF')` → 次の update で発射）と遅延の構造は同じ。
- プレイヤーの向き（facing）は、現行 main の「`touchAimActive` かつ横成分 >= 0.3 で照準へ追従」が砲モードでもそのまま働く（パルスと挙動が揃う。現行の砲ボタン経路では facing は touchPoint に追従しなかった、という差分は意図して受け入れる）。

## 2. モードの明示

「今どちらの武器か」は、視線を移さずに分かる場所に三重に置く。すべて DOM テキスト・CSS・既存描画への相乗りで、新しい描画パスは作らない。

1. **切替ボタンのラベルと色**（§1.1): 現在の武器名を表示し、砲モードではボタンに `.mode-cannon` クラスを付けて色を変える。色はパレットの紫 `#8d62cb` 系の rgba を CSS 側で使う（CSS は 32 色量子化の対象外。ゲーム内描画ではない）。既存の `.tbtn.cancel-armed`（赤）とは色相を分け、「キャンセル予告」と「砲モード」を混同させない。
2. **右スティックの色**: `#touch` に `mode-cannon` クラスを付け、CSS で `.tstick-knob` / `.tstick-base` の色味を紫系に寄せる。スティックは DOM 要素なので量子化にも描画パスにも影響しない。狙っている最中に「このスティックは今、砲を握っている」と指元で分かる。
3. **HUD の武器表示**: 現行の HUD テキスト行（`重粒子砲 n/3 [##--]`）を武器表示に拡張し、現在の武器を角括弧で囲む。例: `武器 [パルス] / 重粒子砲 3/3`、`武器 パルス / [重粒子砲 2/3 ##--]`。溜めゲージの ASCII 表示は砲モード・パルスモードを問わず従来どおり出す（溜めは砲モードでしか起きない）。DOM テキストのみの変更。
4. **溜め発光（既存描画）**: 砲モードでスティックを倒すと、銃口に既存の `drawCharge`（白→青の放射発光、chargeRatio 連動）が出る。パルスには対応する発光が無いため、「倒したら光り始めた = 砲を溜めている」が描画側の明示として働く。コーン（暗幕のライトコーン）は両武器共通で形を変えない。
5. 切り替えの瞬間のフィードバック: アプリ版では既存ハプティクスの枠に相乗りし、切り替え時に Light の impact を 1 回鳴らす（`haptics.ts` に `hapticWeaponSwitch()` を追加。Web では no-op、既存 3 関数と同型）。音は追加しない。

砲モードの「待機中」（スティックに触れていない状態）には、ゲーム内描画に何も足さない。モードの常時表示は DOM 側（ボタン・HUD）が担い、内部バッファの描画は現行のままに保つ。

## 3. 安全策

1. **解放発射の維持**（§1.2): 砲は「倒し続ける」では撃てず、「離す」で初めて撃つ。意図せぬ接触（倒してしまった）だけでは発射しない。
2. **切り替え直後のニュートラル要求**: モードを切り替えた瞬間に右スティックが既に倒れていた場合、そのスティックセッション（指を離すか、mag がデッドゾーン以下へ戻るまで）では、発射も溜め開始も受け付けない（照準の更新だけは受ける）。これにより「パルスを連射しながら切り替えボタンを押した指の流れで、そのまま砲の溜めが始まる」事故と、その逆（砲のつもりが切替直後にパルスが暴発する）を両方向で断つ。時間ベースのロック（○秒間無効）ではなく状態ベース（ニュートラルへ戻るまで）にする: 時間方式は「待てば撃てる」ため、倒しっぱなしの指がロック明けに溜めを始めてしまう欠陥がある。実装は武器モード reducer 内のフラグとして純粋関数化する（§6)。
3. **発射後の自動復帰**: 砲を 1 発撃ったら、自動でパルスモードへ戻す。理由: 砲は「儀式の一手」であり、撃った後のモード滞留こそ誤射の温床になる（次にパルスを撃つつもりでスティックを倒したら、また溜めが始まってしまう）。戻すのは発射が成立したときだけ。キャンセル時・溜め不足の不発時・弾切れ時はモードを維持する（再試行の意図が明確で、勝手に戻ると「撃てたはず」と誤認させるため）。この判断は段階 2 の実機判定で再検討する候補として計画書に残す。
4. **弾切れ時の扱い**: 弾数 0 でも砲モードへの切り替え自体は可能（HUD と切替ボタンの「砲」表示、HUD の `0/3` が手がかり）。スティックを倒しても溜めは始まらない（`Graviton` の `charges > 0` 条件は現行どおり）。弾切れを理由に自動でパルスへは戻さない（回復は 6 秒/発で、戻る・戻らないの往復がかえって混乱を招くため。上記 3 と対で判断を明記する）。
5. **溜め中の左スティック**: 現行の拘束をそのまま維持する。溜め開始（砲モードでスティックがデッドゾーンを超えた）時点で左スティックを強制解放し（現行砲ボタンの `leftStick.release()` 相当）、溜め中は左スティック入力を受けない（現行 `cannonActive` フラグの意味を「砲の溜め中」として再定義し、`applyLeftStick` の抑止と `#touch.aiming` の左スティック減光を流用する）。重要なのは、**砲モードであるだけでは左は拘束しない**こと。拘束は「溜めている間」だけであり、現行との違いは拘束の開始点が「砲ボタンの押下」から「スティックを倒した瞬間」へ移るだけである。砲モードで歩き回り、止まって倒して撃つ、という流れが成立する。
6. **溜め中の切り替え = キャンセル**: 溜め中に切替ボタンが押されたら、溜めをキャンセルしてからパルスへ切り替える（「もう一方へ逃げる」操作として常時有効にする）。ただしタッチでは溜め中の右親指がスティックを保持しており、同じ親指でボタンを押すことは物理的に困難である。したがってタッチでの主キャンセル経路はあくまで「中心へ戻して離す」（§1.3）であり、切替キャンセルは補助経路と位置づける。PC では §5 のとおり主経路になる。この非対称は仕様として明記する。
7. **眺望との優先順位**: 眺望（望ボタン / Shift）中は右スティックがパン操作に使われる現行仕様を優先し、眺望中はスティックによる溜め開始・発射を受け付けない。眺望は「見る」モードであり、武器操作と競合させない（誤射防止としても働く）。

## 4. 既存仕様との整合

- **照準保持**: `heldAim` は武器共通の 1 本とし、モードをまたいで保持する。パルスで狙った方向のまま砲へ切り替えて撃てる（逆も同じ）。モードごとに照準を持ち分けることはしない（持ち分けると「砲に替えたら照準が初期方向へ戻った」という事故になる）。
- **カメラ先行**: パルスモードは現行どおり（照準のみ 2.5 タイル、発射中 5 タイル）。砲モードでスティック照準が有効な間（溜め中を含む）は、最初から拡張側 5 タイルにする。現行の拡張条件 `input.pulseHeld || graviton.chargeRatio > 0` に「砲モードかつ `touchAimActive`」を OR する形で実現する。根拠: 砲は 300 タイルを貫く一撃で、狙う先の視界が価値を持つのは溜め完了を待たず照準の開始時点からであること。溜め発光の有無に関わらず先行が効くため、構えた瞬間に視界が寄る。
- **向き（facing)**: §1.4 のとおり、スティック照準への追従を両モード共通とする。
- **ハプティクス**: 砲の発射 = Heavy（現行 `hapticCannonFire`、不変）。被弾 = Medium、敵撃破 = Light も不変。追加は切り替え時の Light のみ（§2-5)。
- **音**: 変更しない。通過音・環境音はモードに依存しない。

## 5. PC 経路

PC では照準は常時マウス位置であり、モードで変わるのは「左クリック（と発射キー）の意味」だけに絞る。

- **切り替えキー**: `KeyQ` を新設する（`GAME_KEYS` に追加）。WASD の直近で左手のまま届き、既存割当（WASD / Space / KeyF / KeyJ / ShiftLeft / KeyM）と衝突しない。Tab はブラウザのフォーカス移動との衝突と preventDefault の副作用を避けて不採用。マウスホイールでの切り替えは段階 2 の候補とする（wheel イベントの検証基盤が別途要るため段階 1 には入れない）。
- **パルスモード（PC)**: 現行どおり。左クリック長押し / KeyJ で連射、照準はマウス位置。
- **砲モード（PC)**: 左クリックを押している間が溜め（照準はマウス位置＝コーン方向）、離した瞬間に発射（溜め完了時のみ）。現行の KeyF 長押し→解放発射と意味論は同一で、保持する対象が KeyF から左クリックへ移る。
- **キャンセル（PC)**: 溜め中に KeyQ を押すと、溜めをキャンセルしてパルスへ切り替える（§3-6 の「逃げる操作」を PC では主経路化する。マウスとキーボードは別々の手で操作できるため物理的困難がない）。
- **KeyF の扱い**: 統一後は廃止する。ただし段階分け（§6）の都合で、段階 1（タッチのみ）では PC 経路を現行のまま残し（KeyF 従来動作）、段階 2 で PC を切り替え式に統一して KeyF を外す。段階 1 の間だけ PC とタッチで砲の操作が異なる二重仕様になることを、保留として明記する。
- PC でも安全策は共通に適用する: 発射後の自動復帰、弾切れ時の扱い、切り替え直後のニュートラル要求（PC では「切り替えの瞬間に左クリックが押されていたら、その押下では溜めを開始しない」と読み替える）。

## 6. 実装の段階分けと検証

### 段階 1（薄いスライス）: タッチ経路の切り替え式化

範囲: 切替ボタン（旧砲ボタンの置換）、砲モードの右スティック文法（§1.3 の位相）、モード明示（§2 の 1〜4)、安全策（§3 の 1〜7、タッチ分）、カメラ先行の拡張条件、発射後の自動復帰。PC 経路は現行維持。旧砲ボタンのドラッグ経路（`touchPoint` 経由の照準）はこの段階で撤去する（砲のタッチ照準はスティックに一本化する。二経路を残すと `aimAngle` の優先順位が二重化し、誤射経路の検証が倍になるため）。

純粋関数の切り出し（すべて Vitest で固定する。DOM・Canvas には触れない）:

- `src/core/weapon.ts`（新設）: 武器モードの reducer。状態 `{ mode: 'pulse' | 'cannon', needsNeutral: boolean }` とイベント（toggle / fired / neutral 復帰）の遷移を純粋関数にする。固定する性質: 切り替えで mode が反転し needsNeutral が立つこと、発射イベントで mode が 'pulse' に戻ること、キャンセルでは mode が変わらないこと。
- `cannonStickPhase(prev, mag)`: §1.3 の位相遷移（現行 `cannonPhase` のスティック版。置き場所は `touch.ts` の既存純粋関数の隣か `stick.ts`、実装時に決める）。固定する性質: 0.25 超で charging、0.45 以下への後退で cancel-armed、0.45 超への再前進で charging 復帰、境界値ちょうどは含まない（既存テストの流儀に合わせる）。
- 発射可否の判定は新規に作らず、`位相が charging` のときだけ `Graviton` へ held を渡し、解放時に `requestFireCancel` を使うか否かで分ける（発射可否の本体は `Graviton.update` の現行仕様に委ね、二重判定を作らない）。

検証:

- `npm test` / `npx tsc --noEmit` / `npm run build`（AGENTS.md の毎回の検証）。既存の `cannonPhase` テストは、旧経路の撤去に伴い相当分を `cannonStickPhase` のテストへ移す。
- Playwright タッチエミュレーション（pointer: coarse、座標は `getBoundingClientRect()` 実測、CDP タッチ。従来の検証作法どおり）で確認する項目:
  1. 切替ボタンのタップで HUD とボタンの表示が切り替わる。
  2. 砲モードでスティックを倒して 0.6 秒保持→離すと、地形が掘れてビームが出る（発射成立）。
  3. 砲モードで倒してすぐ離すと不発（弾数が減らない）。
  4. 砲モードで倒し、中心（0.45 圏内）へ戻して離すとキャンセル（発射せず、溜め発光が消える）。
  5. パルス連射中に切り替え、そのまま倒し続けても砲の溜めが始まらない（ニュートラル要求）。一度離してから倒すと溜めが始まる。
  6. 砲を撃つと自動でパルスモードに戻っている（HUD / ボタン表示）。
  7. 溜め中は左スティックで移動できない。砲モード（溜めていない）では移動できる。
  8. 項目 4 の「0.45 圏内へ戻す」操作が、実測座標のタッチで無理なく行えるか（§1.3 の保留の決着）。
- スクリーンショット差分: HUD 行と右クラスタの見た目が変わるため、変更前後を同引数で撮り、差分画素数と最大チャンネル差を PR に書く（タッチ UI は DOM のため、撮影はタッチエミュレーション側で行う）。描画パスは増やしていないので frametime の悪化は見込まないが、`render` p50 の前後 2 回計測は AGENTS.md の作法どおり添える。

### 段階 2: PC 経路の統一と仕上げ

範囲: KeyQ 切り替え、PC の砲を左クリックの溜め/解放へ、溜め中 KeyQ = キャンセル、KeyF の廃止、切り替えハプティクス（§2-5 は段階 1 に含めてもよい。実装時に判断し計画書に残す）、ホイール切り替えの可否判断。

検証: キーボード/マウスの Playwright 操作で、Q 切替→左クリック保持→解放で発射、溜め中の Q でキャンセル、KeyF が無効になっていること。既存の PC スクリーンショット（マウス照準系）の差分確認。

### 段階 3（任意・実機判定後）

- 発射後の自動復帰の要否を実機の手触りで再検討する（連続で砲を撃ちたい場面が多いなら、自動復帰をやめてモード滞留に倒す。その場合は滞留時の明示を強める追加策とセットで判断する）。
- 砲モード時のコーン色味の差別化（lighting の色変更に触るため、量子化後の見え方と frametime の計測を添えて別途判断する。本設計の段階 1・2 には含めない）。

## 7. やらないこと

- **新しい描画パスの追加**。モード明示は DOM テキスト・CSS と既存の `drawCharge`・ライトコーンへの相乗りだけに留める。
- **数値の変更**: パルス・砲の性能値（連射間隔、溜め時間、弾数、回復、破壊範囲）とスティックの基礎定数（0.25 / 0.55 / 56px）は変えない。新設する定数は `CANNON_CANCEL_RATIO = 0.45` のみで、根拠は §1.3 に記した。
- **タイル種・ワールド生成への干渉**。決定論・生成には一切触れない（入力系のみ）。
- **32 色量子化の変更**。モード色（紫系）は DOM/CSS 側でのみ使い、内部バッファの描画色は既存パレットの範囲を出ない。
- **照準保持の武器別持ち分け**（§4)。保持照準は 1 本に統一する。
- **砲の連射化・オート照準**など、砲の「一手」の性質を変える変更。
